## §58.1 — Purpose and scope

Two related regressions filed at S37 close (2026-04-28) that both touch the
`background/tabs/` subsystem:

- **B-125 (P0/M)** — Tab claim ownership jump on URL navigation.
  Repro: open `https://xcelenergy.sharepoint.com/` (claimed by bookmark "The
  Source") → click in-page link to a Workday URL → original tab's claim is
  reportedly being released and a new claim opened on a different bookmark
  ("Home - Workday") instead of the original entering a drifted state. Two
  duplicate "Home - Workday" rows appear in sidepanel + a new tab opens each
  time. Reported as a B-099 Option B contract violation.
  See `docs/BACKLOG.md` row B-125.

- **B-121 (P1/M)** — Floating tab opener-chain inheritance regression. Repro:
  any new-tab gesture from a bookmarked page (Ctrl+click, middle-click,
  shift+click, "open in new tab", "open in new window") fails to inherit the
  bookmark's group; new tab appears in Open Tabs section instead of under the
  bookmark. All surfaces affected (sidepanel, standalone, newtab page).
  See `docs/BACKLOG.md` row B-121.

**Why merge into one R0 spike:** both items live entirely within
`background/tabs/` (tab-events.js, tab-claims.js, opener-chain.js,
floating-groups.js, drift.js), the live-state broadcast pipeline, and the
sidepanel render path. Investigating in isolation risks missing cross-cutting
causes (B-099 D-3 contract, opener-chain auto-claim contention,
floating-group runtime visibility). Output decides whether one R3 fixes
both or two parallel R3 fixes are needed.

## §58.3 — B-125 cause enumeration

- **Static-source citation**: `background/tabs/tab-events.js:47-118` (the

  All 6 call sites in the codebase are accounted for at §58.5 below — none
  are in the URL-change path.
- **Likelihood**: **LOW**. The B-099 fix is intact; T7 + T1 are covering
  this exact scenario.

### (b) `releaseClaimByTab` called erroneously from URL-change path

- **Static-source citation**: same as (a).
- **Smoke repro**: same as (a) — T7 would fail.
- **Falsification**: same as (a) — call-site inventory at §58.5.
- **Likelihood**: **LOW** (same as (a) — these are the same hypothesis).

### (c) URL normalization mismatch — new URL normalizes to a different bookmark

- **Static-source citation**: `shared/url.js` `safeNormalizeForMatch`
  (used at `tab-claims.js:100, 113, 129, 207`).
- **Evidence against (for the ORIGINAL tab)**: irrelevant. The original tab

- **Likelihood for B-125-as-stated**: **LOW** for the original tab.

### (d) Multi-window or duplicate-URL disambiguation regression (B-102/B-103 territory)

### (e) `target="_blank"` link spawns a NEW tab; the bug is on the NEW tab, not the original

**This is the most-likely root cause for B-125.**

- **Static-source citation**:
  - `tab-events.js:125-172` — `chrome.tabs.onCreated` listener fires for the
    new tab; runs `recordOpener(tab.id, tab.openerTabId)` then enters async
    `walkOpenerChain` block.
  - `tab-events.js:100-118` — when the new tab's URL resolves (to the Workday
    URL), the `onUpdated` URL-change debounced block fires and calls
    `reevaluateTab(newTabId, workdayUrl, items)`.
  - `tab-claims.js:193-219` — `reevaluateTab`: for the **new** tab,
    `alreadyClaimed = Object.values(claimsMirror).includes(newTabId)` is
    **false** (the new tab is not in any claim). The `if (!alreadyClaimed)`
    branch runs, finds candidates filter-matching items by URL with
    `!(it.id in claimsMirror)`, and assigns the first unclaimed match in
    sortOrder. **If a saved bookmark "Home - Workday" exists with a
    matching URL, it auto-claims the spawned new tab.**
- **What the user observes**:
  1. Original tab (id 100, sharepoint, claimed by "The Source") — claim
     preserved per B-099 Option B. Drift record written if URL changed.
  2. New tab (id 101, opens to Workday) — `walkOpenerChain` returns
     `{groupId: TheSourceGroup, itemId: TheSourceItem}` and
     `appendFloatingGroup` writes a record to `tj:floatingGroups`. **But
     the floating-group record is consumed only on the next cold-start re-
     associate.** Meanwhile `reevaluateTab` runs and assigns the new tab
     to "Home - Workday" — claim now in `claimsMirror`.
  3. On the second click, a third tab (id 102, also Workday) is created.
     `reevaluateTab` runs and the candidates filter
     `!(it.id in claimsMirror)` excludes "Home - Workday" (now claimed by
     tab 101). Tab 102 has no claim → falls into `buildOpenTabs` → renders
     in the Open Tabs section as another "Home - Workday".
  4. UI shows: "Home - Workday" saved row (claimed by tab 101) **plus**
     a "Home - Workday" Open Tab row (tab 102) — visually duplicate.
- **Smoke repro (test)**: see §58.9 "T-125-A". A unit test seeds two
  saved items A (`https://a.example`) and B (`https://b.example`); claims
  A to tab 100; creates tab 101 via `chrome.tabs.onCreated` with `openerTabId: 100`
  and URL `https://b.example`; asserts that B does NOT auto-claim tab 101
  (the new tab) — instead tab 101 should remain a floating-group child of A.
- **Falsification**: if `reevaluateTab` is gated on "tab is not opener-chain-
  inherited", tab 101 stays unclaimed by B. The current code has NO such
  gate.
- **Likelihood**: **HIGH (75%)**. This matches every observable in the
  product-owner repro: ORIGINAL tab claim survives (B-099 holds), NEW tab
  gets auto-claimed by a different bookmark, and repeated clicks add Open
  Tab rows of the same URL. The "duplicate rows" the user sees are (1)
  saved row "Home - Workday" claimed by the first new tab + (2) Open Tab
  row "Home - Workday" for the second new tab.

### (f) `MSG_LIST_ITEMS` post-broadcast filter regression causing duplicate row rendering

- **Static-source citation**: `storage-handlers.js:202-214` — every response
  builds `liveStates`, `driftRecords`, `openTabs`, `windowMap` from the

- **Likelihood**: **LOW**.

### (g) Storage write race in drift partition

- **Static-source citation**: `drift.js:67-79` (`writeDrift`),

- **Likelihood**: **LOW** — drift writes are serialized and B-110 §53 already

### (h) Stale `claimsMirror` causing wrong-item match

- **Likelihood**: **LOW**.

### (i) `reconcileClaims` re-running and re-claiming the wrong tab

- **Static-source citation**: `reconcileClaims` is called once at cold-start

- **Likelihood**: **LOW**.

### (j) Hidden interaction between MSG_NAVIGATE_TO_ITEM AC3 stale-claim repair (B-110) and tab-update events

- **Static-source citation**: `storage-handlers.js:391-404` — AC3 path runs
  `releaseClaimByTab` + `clearDrift` before `chrome.tabs.create`.
- **Evidence against**: AC3 fires only when the user clicks a saved-item row;

- **Likelihood**: **LOW**.

### Summary §58.3 — B-125 most likely cause

**(e) Auto-claim of an opener-chain-spawned tab by a matching unclaimed bookmark
in `reevaluateTab` — HIGH (75%)**.

The B-099 D-3 ("re-claim contention: original wins") test (T7) covers the

## §58.4 — B-121 cause enumeration

### (a) `tab-events.js:165` broadcast scope is `LIVE_STATE` instead of `items`/`openTabs`

- **Static-source citation**: `tab-events.js:165` — `broadcast(SCOPE.LIVE_STATE, 'tab/opener-inherited');`
- **Evidence partially supporting**: `LIVE_STATE` does NOT trigger a structural
  re-render of saved-item rows (it cannot mount a new row that was never in
  `items[]`). However, `refetchAndPatchLiveState` (sidepanel:3014) DOES
  re-fetch full `MSG_LIST_ITEMS` and DOES patch the Open Tabs section via
  `patchOpenTabsSection` (sidepanel:3077). So the LIVE_STATE broadcast
  *does* cause the new tab to appear in Open Tabs — which is exactly the
  current behavior the user reports. The broadcast is firing fine; it's
  just that **the only DOM destination for an unclaimed tab is the Open Tabs
  section**, never under the parent group.
- **Likelihood as the root cause of B-121**: **LOW**. Changing the broadcast
  scope alone wouldn't help — the receiving sidepanel render code has no
  path to mount a tab as a child of a saved-item group.

### (b) `walkOpenerChain` returning null due to claim race

- **Static-source citation**: `tab-events.js:143-148` — `await readyPromise;
  ... const claimsMirror = getClaimsMirror(); const result = walkOpenerChain(...);`
- **Evidence against**: `readyPromise` resolves after `reconcileClaims`
  completes, so `claimsReady === true` and `claimsMirror` is fully populated
  before the walk. For an in-session new-tab gesture (the repro), claims are
  long-since established. No race.
- **Likelihood**: **LOW**.

### (c) `appendFloatingGroup` silent failure under writeTransaction conflict

- **Static-source citation**: `floating-groups.js:142-159` — single-mutator
  `writeTransaction` with retry handled by `write-transaction.js`.
- **Evidence against**: a write conflict would throw; the surrounding
  try/catch at `tab-events.js:143-169` would log a warning. No production
  console-noise reports.
- **Likelihood**: **LOW**.

### (d) Sidepanel render code ignoring floating-group resolution in MSG_LIST_ITEMS response

**This is the root cause for B-121.**

- **Static-source citation**:
  - `storage-handlers.js:202-214` — `MSG_LIST_ITEMS` response shape:
    `{items, liveStates, driftRecords, openTabs, windowMap}`. **The
    response does NOT include floating-group records.**
  - `floating-groups.js` — `tj:floatingGroups` is read **only** by
    `reassociateFloatingGroups`, which runs **only** at cold-start
    (`tabs/index.js:47`). No runtime read path; no enrichment in
    `MSG_LIST_ITEMS`.
  - `sidepanel/sidepanel.js:2014-2110` (renderAll) and 2148-2230
    (buildGroupSection) — group sections are built from `items.filter(i => i.groupId === group.id)`.
    **Floating tabs are not in `items[]`.** They are live-only tabs, not
    saved bookmarks.
  - `open-tabs.js:33-61` (`buildOpenTabs`) — every live tab not in
    `Object.values(claimsMirror)` is included in Open Tabs. Floating-group
    membership has no effect on this exclusion (the tab is not claimed).
- **What's actually happening at runtime**:
  1. New tab opens via opener chain → `appendFloatingGroup` writes to
     `tj:floatingGroups` (correctly).
  2. `LIVE_STATE` broadcast fires → sidepanel calls `MSG_LIST_ITEMS`.
  3. Response: `items` unchanged (no floating-group enrichment); `openTabs`
     includes the new tab; `claimsMirror` does NOT include the new tab.
  4. `patchOpenTabsSection` mounts the new tab in the Open Tabs section.
  5. Group section under "The Source" is built from `items` only — the new
     tab is NOT a saved item, so it doesn't render under the group.
  6. **Outcome: every "tab opened from a bookmark" lands in Open Tabs.**
- **Falsification**: if floating-groups resolved to a "live-only synthetic
  item" injected into the rendered tree under the parent's group,
  `buildGroupSection` would show it. No such code exists today.
- **Likelihood**: **HIGH (90%)**. The design appears to have intended cold-
  start re-association as the only path — runtime "appears under group" was
  never wired. The user's expectation matches the spec language but does not
  match the shipped behavior.

### (e) Newtab + standalone surfaces never wired floating-groups (B-036 / B-035 shipped after B-013/B-018)

- **Static-source citation**: `newtab/newtab.js` — searched for
  `floatingGroup` / `opener-inherited` — zero matches. Same for any
  standalone-window code path.
- **Likelihood as the root cause**: same as (d) — the runtime path doesn't
  exist on **any** surface, including the sidepanel. So this isn't
  "newtab/standalone forgot to wire it" — **no surface has it wired**.
- **Likelihood**: **HIGH (90%)** as a sub-case of (d).

### (f) Opener-chain hop limit (3) exceeded

- **Static-source citation**: `opener-chain.js:58` — `maxHops = 3`.
- **Evidence against**: B-121 repro is one click away from a bookmarked tab
  (1 hop); not implicated.
- **Likelihood**: **LOW**.

### (g) Double-claim race — new tab gets ungrouped-classified before opener-chain async block resolves

- **Static-source citation**: `tab-events.js:125-172` — `onCreated` runs the
  `appendFloatingGroup` async block; meanwhile `onUpdated` may fire when
  the new tab's URL resolves and call `reevaluateTab` (which can auto-claim).
- **Note**: this **IS** the race that drives B-125 (§58.3 cause (e)). For
  B-121 (where the new tab is NOT URL-matching any saved bookmark), the
  auto-claim doesn't fire, so this race doesn't matter. The tab simply ends
  up unclaimed and lives in Open Tabs.
- **Likelihood for B-121**: **MEDIUM** as a contributor when a URL-matching
  bookmark exists, otherwise **LOW**.

### (h) `MSG_LIST_ITEMS openTabs` builder doesn't filter out tabs that are floating-group members

- **Static-source citation**: `open-tabs.js:33-61` — exclusion is solely
  based on `Object.values(claimsMirror)`. Tabs in `tj:floatingGroups` but
  not in `claimsMirror` (the runtime case) are NOT excluded.
- **Likelihood**: this is the correct factual statement of (d) phrased
  differently — the same root cause from a different angle. **HIGH (90%)**.

### (i) NEW: floating-group records keyed by `itemId` of the parent, not the new tab — collision on cold-start re-associate

- **Static-source citation**: `tab-events.js:156-163` — `appendFloatingGroup({ groupId: result.groupId, itemId: result.itemId, ... })` uses the **parent's** itemId.
  `floating-groups.js:103-118` — `claimTabForItem(record.itemId, matchedTabId)` then claims the
  parent's itemId to the new tab. **This OVERWRITES the parent's claim** — the parent
  bookmark's claim now points at the wrong tab.
- **Likelihood**: this is a **separate latent bug** in the cold-start re-association path
  (B-018 / B-001d territory). Not the cause of B-121's runtime symptom, but a real concern
  for any future runtime wiring. **MEDIUM** as a hidden architectural defect; surfaces during R2.

### Summary §58.4 — B-121 most likely cause

**(d) / (h) The sidepanel render path has no runtime read of
`tj:floatingGroups` and no synthetic-item injection — `appendFloatingGroup`
persists the relationship for cold-start only. HIGH (90%).**

The opener-chain inheritance feature (B-013 / B-018) was designed for
cold-start state restoration, NOT for live "new tab appears under parent
bookmark" UX. The user's expectation aligns with the spec language but the
runtime UX was never built.

## §58.5 — Cross-cutting causes (shared between B-125 and B-121)

### (X1) `reevaluateTab`'s auto-claim branch fires unconditionally for new tabs

This is the **shared root**. The function was designed (B-001c) to handle
the `reconcile-on-URL-change` story where a tab that was unclaimed becomes
claimable. The opener-chain feature (B-013) wrote `tj:floatingGroups`
records but did not gate `reevaluateTab` to skip the auto-claim when a tab
is opener-chain-inherited.

- For B-125: the auto-claim *fires* and steals the new tab away from the
  intended parent group, into a coincidentally URL-matching bookmark.
- For B-121: the auto-claim *doesn't* fire (no URL match) but neither does
  any runtime-rendering path — the new tab lands in Open Tabs.

### (X2) `appendFloatingGroup` write has zero runtime visibility

`tj:floatingGroups` is consumed only at cold-start. Every B-013/B-018-era
test asserts the WRITE; no test asserts the new tab appears under the
parent group at runtime. Both bugs sit in the same blind spot.

### (X3) Recent commits surveyed (call-site inventory check)

`git log --oneline -- background/tabs/`: last six commits affecting this
subsystem are listed at §58.11 below. **Neither B-099 (S33) nor B-110
(S36) introduced a new release path or new auto-claim path.** The
`releaseClaimByTab` call inventory in the current tree is exhaustive:

| Site | Path | Compliant with B-099 D-1? |
|---|---|---|
| `tab-events.js:202` | `tabs.onRemoved` | YES — Trigger 1 |

No URL-change release path exists. The B-099 contract holds. **B-125's
"original tab claim is being released" symptom is a misdiagnosis of the

## §58.6 — Most-likely root cause(s)

### B-125

1. **Cause (e) — Auto-claim of opener-chain-spawned new tab in `reevaluateTab`**
   (HIGH, 75%).
   The fix gate: `reevaluateTab` should skip the auto-claim branch for any
   newly-created tab that walked an opener-chain to an inherited group. The
   contract: a tab that has been associated with a parent group via opener-
   chain is "spoken for" — it must not silently claim a different saved item.

2. **Secondary — `appendFloatingGroup` parent-itemId reuse latent bug** (MEDIUM, 25%).
   The cold-start re-associate path uses the parent's `itemId` to claim the
   floating tab, which would overwrite the parent's own claim. This is
   latent today (no runtime path uses it for B-125 repro) but is a
   correctness bug that R2 should redesign.

### B-121

1. **Cause (d) / (h) — No runtime floating-group → render path** (HIGH, 90%).
   The fix gate: `MSG_LIST_ITEMS` response must enrich with the live
   floating-group membership and the sidepanel render path must inject
   synthetic "floating tab" rows under the parent group. Open Tabs must
   exclude any tab that has a floating-group record.

2. **Secondary — Synthetic-item identity model** (MEDIUM, 10%).
   What is the row's `data-key`? `tab:<tabId>` (ephemeral) or
   `floating:<groupId>:<tabId>` (still ephemeral)? B-124's design discussion
   becomes coupled to the answer here — visual distinction depends on a
   stable identity primitive.

### Cross-cutting

Both bugs share **§58.5 X1 + X2** — the `reevaluateTab` auto-claim was never
gated on opener-chain inheritance; floating-groups were never wired to runtime
render. Fixing one without the other will leave UX gaps.

## §58.7 — R3 fix structure recommendation

**Choice: (B) Two separate R3 fixes — distinct code paths, can run in
parallel under the cross-item parallelization rules (P-3: max two M items
in parallel).**

### B-125 R3 fix sketch

- **Files touched** (estimate):
  - `background/tabs/tab-claims.js` — gate `reevaluateTab`'s auto-claim
    branch (~10-20 LOC, plus contract comment).
  - `background/tabs/tab-events.js` — record "opener-chain-inherited"
    marker for new tabs, surface to `reevaluateTab` (~10-20 LOC).
  - Possibly a new in-memory `inheritedTabs: Set<number>` (ephemeral, like
    `openerMap`) (~10 LOC).
- **Total LOC**: ~50 LOC across 2-3 files.
- **Tests**: 3-5 new tests in a new `tests/b125-claim-inheritance-gate.test.js`.
- **Effort**: M (Full Pipeline). 1 day-ish.

### B-121 R3 fix sketch

- **Files touched** (estimate):
  - `background/messages/storage-handlers.js` — enrich `MSG_LIST_ITEMS`
    response with `floatingMembers: Record<groupId, OpenTab[]>` derived
    from `tj:floatingGroups` ∩ `liveTabIndex` minus `claimsMirror` (~30 LOC).
  - `background/tabs/open-tabs.js` — exclude floating-group members from
    `buildOpenTabs` (~5-10 LOC).
  - `shared/messages.js` — extend `ListItemsResponse` typedef to include
    `floatingMembers` (contract change; **B-119 / B-126 enumeration applies**).
  - `sidepanel/sidepanel.js` — `buildGroupSection` accepts floating members,
    renders "live-only synthetic items" under the parent group (~50 LOC);
    `refetchAndPatchLiveState` updates floating section on broadcast (~30 LOC);
    open-tab row builder factored out for reuse (~20 LOC).
  - `newtab/newtab.js` and `standalone/` — same render extension (~30-50 LOC each).
- **Total LOC**: ~150-200 LOC across 4-6 files.
- **Tests**: 5-8 new tests covering both the SW response shape and the
  sidepanel render injection.
- **Effort**: M (Full Pipeline). 1.5-2 days.

### Why not (A) Single R3

The two bugs share a subsystem but their fix surfaces are largely disjoint:
- B-125 = **gate in `reevaluateTab`** (background, no message-contract change).
- B-121 = **enrich `MSG_LIST_ITEMS` + sidepanel render** (background +
  message-contract change + sidepanel + newtab + standalone).

Bundling them risks (i) blast radius, (ii) one being blocked on the other's
review cycle, (iii) confusing rollback boundaries. Two PRs land cleanly.

### Why not (C) Sequential

Neither fix changes invariants the other depends on. B-125's fix narrows
the auto-claim path; B-121's fix adds a render path. They commute.

### Recommended landing order

If parallel slots are tight: **B-125 first** (P0, smaller, narrower blast
radius), then B-121 (P1, larger, contract change). If both can run in
parallel: launch both R1 immediately.

- **Story (lock as filed)**: see BACKLOG B-125 row.
- **Concrete behaviors / ACs to lock**:
  - **AC1** — Tab `T_orig` claimed by item `A`. New tab `T_new` is opened
    via opener-chain from `T_orig`. Even if `T_new`'s URL matches saved
    item `B` (where `B != A`), `T_new` does NOT auto-claim `B`.
    Instead `T_new` either (i) renders as a floating-group child of A
    (post-B-121 fix), or (ii) lives in Open Tabs (pre-B-121 fix) — but
    NEVER as a `B`-claimed live tab.
  - **AC2** — The `T_orig` → `A` claim is preserved across `T_orig`'s URL
    navigation (B-099 D-1 regression guard).
  - **AC3** — If `T_orig` is closed, `A`'s claim is released (B-099
    Trigger 1).
  - **AC4** — A subsequent new tab `T_new2` (also opened via opener-chain
    from `T_orig`, also URL-matching `B`) ALSO does not auto-claim `B`.
    Both `T_new` and `T_new2` remain inheritance children of `A`'s group.
  - **AC5** — A user-initiated tab (NOT opener-chain — `chrome.tabs.create`
    from address-bar / new-tab button / `chrome.tabs.create` from
    `MSG_NAVIGATE_TO_ITEM`) STILL auto-claims a URL-matching unclaimed
    bookmark (regression guard for B-001c "auto-claim of newly-opened
    bookmark URL").
  - **AC6** — Promotion path (`MSG_PROMOTE_TAB` on a floating-group-child
    tab) explicitly creates a saved item and claims the tab to it. Existing
    behavior preserved.
- **Destructive-action confirmation (DoR item 7)**: N/A — claim mutations
  do not surface destructive UX. Rationale: a misclaimed tab is recoverable
  by closing the spawned tab or running MSG_DEMOTE_ITEM, both of which have
  their own confirmations where required.
- **Selector audit (rehome items)**: N/A — no DOM rehoming.
- **Performance acceptance criteria**: no regression in
  `chrome.tabs.onCreated` handler latency; `reevaluateTab` runtime
  unchanged.

### B-125 — what R2 needs to design

- **Storage schema impact**: NONE. `claimsMirror` is unchanged.
- **Message contract changes**: NONE.
- **New in-memory state**: an `inheritedTabs: Set<number>` (ephemeral,
  mirrors `openerMap` pattern in `opener-chain.js`). Cleared on tab
  removal (`pruneOpener` symmetry).
- **C-3 SW cold-start safe**: an `inheritedTabs` set is in-memory only. On
  SW cold-restart, the set is empty — but `reconcileClaims` runs and the
  cold-start path establishes claims from URL match. The "lost"
  inheritance marker is acceptable (cold-start re-association via
  `tj:floatingGroups` is the recovery path).
- **C-4 ID stability**: tabIds are ephemeral; the inheritance gate only
  needs to survive within a single browser session.
- **B-126/B-119 enumeration**: NO new contract change in the canonical
  contract-types list (DOM/ARIA/message/CSS-token). The
  `reevaluateTab` gate is an internal behavior change only. R2 fix-scope
  table notes test files affected: `tests/b099-drift-fix.test.js` (T7
  re-claim contention — should still pass); new `tests/b125-*.test.js`.

### B-121 — what R1 [product-manager] should lock

- **Story (lock as filed)**: see BACKLOG B-121 row.
- **Concrete behaviors / ACs to lock**:
  - **AC1** — A new tab opened via opener-chain from a bookmarked saved
    item appears as a "floating tab" row UNDER the parent's group section
    in the sidepanel.
  - **AC2** — The same row appears in newtab and standalone surfaces.
  - **AC3** — The floating tab row does NOT appear in the Open Tabs

  - **AC4** — Visually distinct from saved-bookmark rows? — DEPENDS ON

  - **AC5** — Closing the floating tab removes it from the group section.
  - **AC6** — Reloading the browser restores the floating tab as a child
    of its group (cold-start re-associate via `reassociateFloatingGroups`

  - **AC7** — Promote-to-bookmark path (`MSG_PROMOTE_TAB`) on a floating

  - **AC8** — All gestures inherit (Ctrl+click, middle-click, shift+click,

- **Selector audit (rehome items)**: N/A — no element is being rehomed

### B-121 — what R2 needs to design

- **Storage schema impact**:
  - `tj:floatingGroups` shape unchanged in storage.
  - **Latent bug from §58.4(i)**: `appendFloatingGroup` uses the parent's
    `itemId` for the new floating tab. R2 must redesign — either generate
    a synthetic floating-tab id (e.g., `floating:<ulid>`) and store it in
    the record, or change the record's identity model so cold-start
    re-associate doesn't overwrite the parent's claim. **Storage schema
    version bump candidate.**
- **Message contract changes**: `MSG_LIST_ITEMS` response gains
  `floatingMembers: Record<groupId, OpenTab[]>` (or alternatively
  `floatingTabs: Array<{groupId, tabId, ...}>`). **This IS a contract
  change** — B-119 R2 fix-scope test-assertion enumeration applies +

- **Broadcast scope**: `tab/opener-inherited` broadcast scope reviewed —
  changing from `LIVE_STATE` to `ITEMS` would force a more expensive full
  re-render. Recommendation: keep `LIVE_STATE` AND extend
  `refetchAndPatchLiveState` to handle the new floating-member section

- **C-2 message contracts typed**: `floatingMembers` must be defined in
  `shared/messages.js` typedef.
- **C-3 SW cold-start safe**: cold-start path unchanged
  (`reassociateFloatingGroups` runs); plus `MSG_LIST_ITEMS` enrichment
  works equally well from the same in-memory data sources.
- **C-9 Empty-state design**: a group with zero saved items but with
  floating members — does the section render? What about a group with
  zero of either? Document.
- **C-11 Popup-lifecycle message ordering**: not implicated.
- **Render-path changes in sidepanel.js**: see §58.7 fix sketch — significant
  refactor of `buildGroupSection` and `refetchAndPatchLiveState`.
- **B-119 R2 fix-scope test-assertion enumeration**: applies. Pre-existing
  tests asserting MSG_LIST_ITEMS response shape:
  - `tests/b099-drift-fix.test.js` T6 (lines 282-308) — asserts buildOpenTabs

- **B-126 CSS-token expansion**: not relevant for B-121; the contract
