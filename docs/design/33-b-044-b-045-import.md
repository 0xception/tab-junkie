## §33 — B-044 + B-045 — Collection Import (R2 Design + R6 Close for B-044)

**Status:** R2 design (both items) + R6 close for B-044 (shipped Sprint 18, v1.13.0). B-045 design is live and unchanged — stub `background/import/json-validator.js` ships in B-044 throwing `ERR_INVALID_FORMAT` until Wave 4 builds B-045.

### §33.1 Overview

B-044 (Netscape HTML import) and B-045 (Tab Junkie JSON-backup import) together complete the **data-portability round-trip** opened by §32 (Sprint 17 export). They are designed and shipped as one architectural unit in Sprint 18 because they share:

- a single sidepanel entry point (the overflow-menu "Import" submenu adjacent to the existing "Export" entries),
- a single file-picker → parse → count-preview → Replace-all-confirm → commit flow,
- a single message contract (`MSG_IMPORT_COLLECTION` with a `format` discriminator), and
- a single atomic writeTransaction at the commit boundary.

Both features are **replace-only** at v1 — the imported file overwrites `tj:items`, `tj:groups`, and (when present) `tj:prefs` in a single transaction. Merge-on-import is explicit out-of-scope (§33.14). Per Sprint 17 retro D-3, partial-partition writes on import are the known symmetric race to avoid, so the commit stage is a single `writeTransaction` spanning every affected partition.

The two formats serve complementary intents:

- **B-044 (HTML)** is an **ingress-only interchange** format. Incoming files come from Chrome's `chrome://bookmarks` export, Firefox's Library Export, Edge Favorites Export, Safari's Bookmarks.html, and every third-party bookmark manager that speaks Netscape Format 1. Fidelity is bounded to what the format carries (title, URL, folder name, ADD_DATE, LAST_MODIFIED, ICON).
- **B-045 (JSON)** is a **round-trip-safe backup restore**. It consumes the frozen §32.5 allow-list (locked by B-067, merged `2e4e507`). A file produced by B-043 on schemaVersion N, imported by B-045 on the same version, MUST produce byte-equivalent `tj:items` and `tj:groups` partitions (B-043 AC7, modulo ULID re-minting rules in §33.8).

**Scoped assumption (frozen):** imports always mint fresh ULIDs for every item and group — file-provided IDs are never reused. This is a deliberate divergence from B-043's round-trip byte-equality promise: B-043 exports whatever ULID is in storage, but B-045 re-mints. The reason is defence against adversarial files that craft colliding ULIDs; see §33.8.

### §33.2 Module Layout

**Decision: four files under a new `background/import/` directory, plus two modification points.** Rationale mirrors §32.2: co-locate parse logic with the commit path, keep each builder under ~150 lines for tractable R4 review, keep the shared schema constants in `shared/` so the importer and exporter reference identical symbols.

```
background/

    index.js            NEW — single entry `importCollection({ format, content, options }) → ImportResult`.
                           Dispatches on format; owns the top-level try/catch that normalizes any parser
                           throw to a typed `StorageError`.
    html-parser.js      NEW — Netscape DL/DT/A/H3 walker. Uses DOMParser('text/html') — NEVER innerHTML.

                           (2) read the file to text via `FileReader.readAsText`, (3) dispatch
```

**Why separate `html-parser.js` and `json-validator.js` from `commit.js`:** parse and commit have different failure modes and testability needs. Parse is pure (input string → `{ items, groups, repairs }`), easy to unit-test against seeded fixtures without a chrome-mock. Commit is stateful (ULID mint + writeTransaction). Splitting keeps each file focused and makes the test-engineer's R5 fixture work tractable.

**Why `commit.js` and not two format-specific committers:** after parse, the shapes converge. Both parsers emit `{ items: Item[], groups: Group[], preferences?: Preferences, repairs: RepairReport }`. The ULID re-mint, cross-reference rewrite, and writeTransaction are identical. One committer keeps the D-3 atomicity guarantee in one place.

**Why NOT a single `import/parser.js`:** HTML and JSON parsers share zero logic. A combined file would be two functions under one roof — no abstraction value, and a larger R4-review surface.

### §33.3 Message Contract

**Decision: unified `MSG_IMPORT_COLLECTION` with a `format` discriminator (mirrors §32.3 `MSG_EXPORT_COLLECTION`).**

```js
// shared/messages.js — appended after the Data-export block (after MSG_EXPORT_COLLECTION).

// ---- Data import (B-044 / B-045) ----
/**
 * Import a user-supplied collection file, replacing all existing data atomically.
 * Write path: gated by the safe-mode guard (rejects with ERR_SAFE_MODE). On success
 * broadcasts scope 'items' so open surfaces re-fetch (B-050 pattern).
 */
export const MSG_IMPORT_COLLECTION = 'tj/importCollection';

/**
 * @typedef {Object} ImportCollectionRequest
 * @property {'html' | 'json'} format
 *   'html' parses Netscape Bookmark File Format 1 (B-044).
 *   'json' parses Tab Junkie schema-v1 backup (B-045).
 * @property {string} content
 *   Raw file text (UTF-8). The sidepanel reads the user-picked File via
 *   FileReader.readAsText before dispatching; Blob/File objects do NOT cross
 *   the message boundary (structured-clone overhead + test-harness friction).
 * @property {Object} [options]
 * @property {boolean} [options.skipDuplicates=true]
 *   B-060 hook. Default true (skip duplicates). B-060 flips the default via UI;
 *   B-044/B-045 always pass true.
 */

/**
 * @typedef {Object} ImportCollectionResponse
 * @property {number} itemsImported     Count of items written to tj:items post-repair.
 * @property {number} groupsImported    Count of groups written to tj:groups post-repair.
 * @property {number} duplicatesSkipped Count of duplicate-URL items dropped (in-file duplicates only).
 * @property {RepairReport} [repairs]   B-045 only — structured auto-repair breakdown.
 *                                      Omitted for B-044 (HTML has no repair surface — malformed
 *                                      entries counted under `skipped` instead).
 * @property {number} [skipped]         B-044 only — malformed-entry skip count (AC10).
 *
 * On success: { ok: true, data: ImportCollectionResponse }.
 * On failure: { ok: false, error: { code: 'ERR_*', message: string } }.
 */

/**
 * @typedef {Object} RepairReport
 * @property {number} orphanedGroups     Groups reparented to null (AC5).
 * @property {number} cyclesBroken       parentId cycles broken (AC6).
 * @property {number} duplicateIds       Records assigned fresh ULIDs (AC7).
 * @property {number} orphanedItems      Items moved to Ungrouped (AC8).
 * @property {number} duplicateUrls      In-file URL dedup drops (AC12).
 * @property {boolean} preferencesSkipped  True if imported prefs were shape-invalid (AC10).
 */
```

**Payload validation (handler-side, non-negotiable per C-2):**

```
- typeof p === 'object' && p !== null
- p.format === 'html' || p.format === 'json'
- typeof p.content === 'string' && p.content.length > 0
- If p.options, typeof p.options === 'object' && (p.options.skipDuplicates === undefined || typeof p.options.skipDuplicates === 'boolean')
  → Any violation → throw StorageError(ERR_VALIDATION, 'importCollection: bad payload').
- Unknown fields ignored (forward-compat posture, matches §32.3).
```

**Safe-mode classification:** `MSG_IMPORT_COLLECTION` is a WRITE operation — it MUST be in `WRITE_MESSAGE_TYPES` in `storage-handlers.js` so the safe-mode gate blocks imports under schema-downgrade with `ERR_SAFE_MODE`. B-044 AC12 and B-045 AC3 both require this.

**Broadcast classification:** `MSG_IMPORT_COLLECTION: 'items'` in `MUTATION_BROADCASTS` — a single `MSG_STATE_CHANGED { scope: 'items' }` broadcast after commit. Sidepanel re-fetches via `MSG_LIST_ITEMS`. Groups and preferences changes ride the same broadcast (receivers already re-fetch the full tree on `scope: 'items'`). No per-partition broadcast storm.

**Note on "preview THEN commit" (two round-trips):** a single-round-trip "parse+commit" would require the sidepanel to know the counts BEFORE the user confirms — which means either the SW must stash parser output across a confirm round-trip, or the file must be parsed twice (once for preview, once for commit).

**Decision: parse twice.** Rationale:

1. Parse is pure and fast (< 500ms P95 at 1000 items per §33.11) — two parses is budget-safe.
2. Stashing parsed output in SW memory between round-trips is a cold-start-safety violation (C-3): an SW restart between "preview" and "commit" loses the cached parse, forcing a re-parse anyway.
3. `storage.session` stashing works but adds a new partition-like key, widens the D-3 atomicity surface (commit must now also clear the stash), and pollutes cold-start logic for zero user benefit.
4. The alternative — a single long-lived message handler that awaits the user's dialog choice — would block the SW handler for arbitrary user time, risking SW auto-suspend.

The commit round-trip passes `commit: true` to signal "skip preview, write now." The parse cost is paid twice; at 1000 items that's < 1s doubled, still inside the AC14 (B-044) / AC13 (B-045) budget.

### §33.5 Parse Detail — HTML (B-044)

**As shipped: hand-rolled Netscape tokenizer (string-scan), NOT `DOMParser`.** R2 originally specified `DOMParser('text/html')`. During R3 build the engineer discovered MV3 service workers have no DOM — `DOMParser`, `document`, and `window` are all `undefined` in the SW global scope. A DOMParser-based path would have required forking parse out of the SW (offscreen document or sidepanel-side parsing), widening the attack surface and the architecture.

**Decision (permanent, R6): the hand-rolled tokenizer is architecturally SAFER than the DOMParser path and is the shipping design.** Both [code-reviewer] and [security-reviewer] endorsed the switch in R4. Security rationale:

1. **Text-only by construction.** The tokenizer consumes a string and emits records; it never builds a DOM tree. There is no node to `.innerHTML` accidentally, no script to execute, no parser quirk to exploit.
2. **Bounded tag subset.** Scanner recognises only the Netscape 1996 tag subset: `<DL>`, `<DT>`, `<A>`, `<H3>`, `<P>` (ignored), `<HR>` (ignored). Any other tag is skipped as literal text.
3. **Bounded entity subset.** Six named entities (`&amp; &lt; &gt; &quot; &#39; &apos;`) plus decimal/hex numeric character references capped at `0x10FFFF`. No entity-expansion DoS surface.
4. **Zero DOM dependency.** Works from the SW without an offscreen document, without a sidepanel-side parse-then-resend round trip, without any new `chrome.*` permissions.

This decision supersedes the `DOMParser` directive in the original R2 text. Do not revert. If a future backlog item wants to add a feature the current tokenizer cannot express (e.g., richer microdata), it must justify the SW-DOM-absence constraint explicitly — not assume DOMParser is available.

**Walk algorithm (depth-first, as shipped):**

```
parseNetscape(content):
  1. tokens = scanNetscape(content)   // hand-rolled tokenizer — emits TAG_OPEN/TAG_CLOSE/TEXT events
  2. Validate doctype token: must be <!DOCTYPE NETSCAPE-Bookmark-file-1> (case-insensitive)
     → Missing / wrong → throw StorageError(ERR_INVALID_FORMAT, 'Not a Netscape bookmarks file')
  3. Locate root <DL>
     → Missing → throw StorageError(ERR_INVALID_FORMAT, 'No <DL> root found')
  4. items = [], groups = [], skipped = 0, duplicateUrls = 0
     seenUrls = new Set()
  5. Recurse with rootDL, parentGroupId = null, ancestorPath = []
     For each direct <DT> child of the <DL>:
       (a) If <H3> child present → this is a FOLDER.
           - name = h3.textContent.trim()
           - addDate = attrToEpochMs(h3.getAttribute('ADD_DATE'))
           - modDate = attrToEpochMs(h3.getAttribute('LAST_MODIFIED'))
           - If ancestorPath.length + 1 > 2:
               — flatten: displayName = [...ancestorPath, name].join(' / ')
                          parentForThisGroup = topLevelGroupId (the oldest ancestor)
               — emit group record { id: ulid(), name: displayName, parentId: topLevelId, ... }
           - Else if ancestorPath.length + 1 === 2:
               — emit as sub-group: parentId = topLevelGroupId
           - Else (top level):
               — emit as top-level group: parentId = null
               — topLevelGroupId = this group's newly-minted id
           - Recurse into this folder's child <DL> with ancestorPath + [name]
       (b) Else if <A> child present → this is an ITEM.
           - href = a.getAttribute('HREF')
           - title = a.textContent  (NEVER innerHTML — B-044 AC15)
           - icon = a.getAttribute('ICON')  — see favicon decision below
           - If href missing, or normalizeUrl(href, { forStorage: true }) throws → skipped++, continue
           - If title is empty/whitespace, fall back to href; if still empty → skipped++, continue
           - If title length > MAX_TITLE → truncate (not skip — AC10)
           - Normalize URL → normalized
           - If skipDuplicates && seenUrls.has(normalized) → duplicateUrls++, continue
           - seenUrls.add(normalized)
           - emit item record { id: ulid(), title, url: normalized, groupId: currentGroupId,
                                 createdAt: addDate, updatedAt: modDate, sortOrder: seqInGroup++ }
       (c) Else → ignore (unknown <DT> content; forward-compat)
  6. Return { items, groups, preferences: undefined, repairs: { duplicateUrls }, skipped }
```

**`attrToEpochMs(str)`:** `Number.parseInt(str, 10)` — if finite and `>= 0` and `<= 4102444800` (Jan 1 2100 in seconds), multiply by 1000. Else fall back to `Date.now()`. Per B-044 AC9, missing/invalid timestamps do NOT skip — they default.

**Depth-flattening algorithm (B-044 AC6, exact spec):**

- Depth 0 = root `<DL>`.
- A `<H3>` inside the root `<DL>` creates a depth-1 group with `parentId: null`. Its items (direct `<A>` children of the folder's `<DL>`) import with `groupId = <this group's id>`.
- A `<H3>` nested inside a depth-1 folder creates a depth-2 group. Because Tab Junkie caps group depth at 1, depth-2 groups flatten: `displayName = parentName + ' / ' + childName`. Parent of flattened group = the depth-1 ancestor's id (not null, not a new synthetic top-level).
- A `<H3>` nested at depth ≥ 3 flattens further: `displayName = grandparent + ' / ' + parent + ' / ' + child`. Parent remains the depth-1 ancestor. No items are dropped; every `<A>` at any depth survives under the nearest flattened group.
- Example: `Work/Projects/2026/item.html` → top-level group "Work", sub-group "Projects / 2026" (parentId = Work's id), item under "Projects / 2026".
- Edge case: a `<H3>` that's the *first* folder in the document (no `<A>` before it) still parents its items to itself; top-level `<A>` entries NOT nested in any `<H3>` import with `groupId = null` (B-044 AC7 — the `__ungrouped__` sentinel, no synthetic "Ungrouped" group).

**Favicon handling (`<A ICON="data:…">`):** **Decision: drop.** Three reasons:

1. **Security:** `ICON` can be an arbitrary `data:` URL. Persisting it into `tj:items` would let a crafted import file embed arbitrary base64 payloads of arbitrary size directly into storage. The B-058 `ALLOWED_URL_SCHEMES` list excludes `data:` for exactly this threat model; applying that allow-list to favicons (which have no such gate) would create a schema mismatch.
2. **Size:** A 48×48 PNG favicon base64-encoded is ~4 KB; 1000 items with inlined favicons = 4 MB — a quarter of the 5 MiB `chrome.storage.local` quota, gone for cosmetic data that `buildLiveStates` already supplies at runtime from the live tab when the bookmark is opened.
3. **Schema:** Today's Item shape has no `faviconUrl` field (§32.5.2). Adding one solely to populate it from imported `ICON` values is a storage-schema expansion that requires a migration and an export-side round-trip design refresh. Out of scope for B-044.

The parser reads and ignores `ICON`. Per §33.15 Q-1, if a future backlog item adds persisted favicons, the parser upgrades with one branch, not a redesign.

**Group color assignment (B-044 AC8):** djb2 hash of final display name, mod `GROUP_COLORS.length`. Deterministic. See §33.9 for the shared hash helper.

**XSS test probe (B-044 AC15):**

- Input file contains `<A HREF="javascript:alert(1)">title-with-script</A>` and a bookmark with title `</A><script>alert(1)</script>`.
- `HREF="javascript:"` → `normalizeUrl` rejects → `skipped++`, item not persisted. No script execution (B-058 allowlist).
- Title `</A><script>…</script>` → tokenizer treats `<script>` as a literal text character sequence inside the `<A>` body (not a parser-recognised tag). The resulting title is an entity-decoded string imported as `.textContent` into the sidepanel DOM at render time. Never interpreted as markup because the tokenizer never builds a DOM.

### §33.6 Parse Detail — JSON (B-045)

**Parser: native `JSON.parse(content)`.** Never `new Function`, never `eval`, never `Function.prototype.call.bind` tricks.

**Root validation (B-045 AC2, against §32.5.1):**

```
validateAndRepair(content):
  1. root = JSON.parse(content)
     → throw → ERR_INVALID_FORMAT
  2. If typeof root !== 'object' || root === null || Array.isArray(root) → ERR_MALFORMED_ROOT
  3. If typeof root.schemaVersion !== 'number' || !Number.isInteger(root.schemaVersion) || root.schemaVersion < 1 → ERR_MALFORMED_ROOT
  4. If typeof root.exportedAt !== 'string' → ERR_MALFORMED_ROOT
  5. If !Array.isArray(root.items) || !Array.isArray(root.groups) → ERR_MALFORMED_ROOT
  6. If root.preferences !== undefined && (typeof root.preferences !== 'object' || root.preferences === null) → ERR_MALFORMED_ROOT
  7. Schema-version gate:
       a) root.schemaVersion === KNOWN_VERSION → proceed
       b) root.schemaVersion < KNOWN_VERSION → apply in-memory MIGRATION_STEPS chain (B-001b) to root snapshot,
          then proceed. (This is a clean reuse of the same array — the import snapshot is just a {items, groups,
          prefs, meta:{schemaVersion}} shape passed through migrate().)
       c) root.schemaVersion > KNOWN_VERSION → ERR_UNKNOWN_SCHEMA_VERSION
  8. Repair pass (in-order):
       a) Duplicate IDs (AC7) — iterate items, assign fresh ULID on collision; record old→new map per record.
       b) Duplicate IDs for groups — same.
       c) Rewrite cross-references: any items[i].groupId matching a remapped group id → new id (if the rename
          preserved the intended link per AC7's disambiguation rule: "links follow the last-written duplicate").
       d) Circular parentId refs (AC6) — break the junior edge (higher createdAt, then higher id as tiebreak).
       e) Orphaned sub-groups (AC5) — any group.parentId not resolving to a live group → null.
       f) Orphaned items (AC8) — any item.groupId not resolving to a live group → null.
       g) Allow-list strip (AC9) — filter every item/group through sanitizeItem / sanitizeGroup from
          json-export.js (or the shared module they live in — see §33.15 Q-2).
       h) Duplicate URLs in file (AC12) — sort items per §32.5.5, dedup by normalizeUrl(url); drops counted.
  9. Preferences validation (AC10):
       If root.preferences is present: validate each key against §32.5.4 enums/types.
       Any invalid → set preferencesSkipped=true, omit preferences from commit.
       Else: pass preferences through verbatim (forward-compat for unknown keys, matches §32.16.3 D-2).
  10. If the repaired items array is empty AND groups array is empty AND source was non-empty:
      → ERR_UNREPAIRABLE (defensive — likely a malformed file that mass-failed repair).
  11. Return { items, groups, preferences?, repairs: RepairReport }.
```

**Migration chain reuse (B-045 AC3):** `MIGRATION_STEPS` in `background/storage/migration.js` is a static array of `{ fromVersion, toVersion, migrate(snapshot) }`. The storage runner applies them to a live snapshot; the importer applies them to the imported object. `migrate()` must therefore be shape-compatible — it operates on `{ meta: {schemaVersion}, items, groups, preferences }` regardless of source. Today `MIGRATION_STEPS` is empty (KNOWN_VERSION = 1), so B-045 touches no migration step in Sprint 18 — but the reuse contract is documented here so Sprint N+1's first real migration covers both paths.

**Allow-list consumption (C-7 from Sprint 17 retro):** the B-067 Wave 1 allow-list is the authoritative field gate. R3 MUST iterate the allow-list (not the input keys) when filtering — the same pattern as `sanitizeItem` / `sanitizeGroup` in `background/export/json-export.js:86–108`. R4 [security-reviewer] greps for the inverse pattern (`for (const key of Object.keys(item))` inside the importer) and flags it as HIGH.

**Duplicate-ID disambiguation rule (AC7 edge):** "links follow the last-written duplicate." Rationale: the count-preview dialog shows the imported data as it will appear post-commit; users will expect the *last* version of a same-id record to win, because that matches "later writes override earlier writes" intuition. Formally: iterate items/groups in §32.5.5 order; for each duplicate, the first occurrence keeps the id, subsequent occurrences mint fresh ULIDs; any later reference to that id resolves to the most-recently-renamed target. Default path: if no reference is ambiguous, the renamed records become independent.

### §33.7 Atomicity + Storage Impact (C-1)

**Decision: single `writeTransaction` spanning all affected partitions.** Sprint 17 D-3 retro explicitly flagged partial-partition imports as the symmetric write race to eliminate.

**Partitions written in one transaction:**

| Partition | Final state on success |
|---|---|
| `tj:items` | `[...importedItems]` — full replacement |
| `tj:groups` | `[...importedGroups]` — full replacement |
| `tj:prefs` | If AC10 applies: `{ ...DEFAULT_PREFERENCES, ...importedPreferences }`. Else untouched (ops array does NOT list PARTITION_PREFS) |
| `tj:meta` | Untouched — schemaVersion remains at KNOWN_VERSION post-import (migration was applied in-memory to the imported snapshot; the on-disk schema is already at the current version) |

**Partitions reset via a SECOND writeTransaction (as shipped):**

| Partition / store | Reset action | Why reset |
|---|---|---|
| `tj:drift` | Second `writeTransaction` op — mutator returns `{}` | Pre-import drift records reference deleted item ids; stale entries pollute `buildLiveStates` |
| `tj:floatingGroups` | Second `writeTransaction` op — mutator returns `[]` | Pre-import floating-group records reference deleted item ids and groupIds |
| `storage.session.TabClaims` | `chrome.storage.session.remove('tj:tabClaims')` — best-effort | Pre-import tab claims reference deleted item ids |

**Two-writeTransaction pattern — as shipped:** the primary `writeTransaction` writes `tj:items` + `tj:groups` + optional `tj:prefs` atomically. A SECOND `writeTransaction` resets `tj:drift` + `tj:floatingGroups` atomically. The session-storage claims wipe is a best-effort follow-up (transient store, self-healing).

**Why two transactions rather than one:** the acceptable failure mode is "items/groups imported, drift/floating briefly stale until the reset transaction runs" — both partitions self-heal lazily anyway (drift clears at read time, floating rebuilds on tab events). The unacceptable failure mode is "items partially written or groups partially written" — hence the primary transaction is its own atomic unit. The reset transaction is intentionally separated so a drift/floating-only failure cannot roll back a successful items/groups commit. Pattern matches Sprint 17 D-3 retro: keep atomicity boundaries tight, make transient-state resets independent.

**This is consistent with B-017's partial-atomicity pattern** (§5 note on `MSG_DEMOTE_ITEM`): steps 2–4 of demote are not transactional because the downstream failure modes are self-healing. Same principle applied.

**Post-commit sequence (in order, single awaited path — as shipped):**

```
commit.js commitImport({ items, groups, preferences? }):
  1. primaryOps = [{ partitionKey: partitionKey(PARTITION_ITEMS), mutator: () => items },
                   { partitionKey: partitionKey(PARTITION_GROUPS), mutator: () => groups }]
  2. If preferences: primaryOps.push({ partitionKey: partitionKey(PARTITION_PREFS),
                                       mutator: () => ({ ...DEFAULT_PREFERENCES, ...preferences }) })
  3. await writeTransaction(primaryOps)   // atomic — D-3 lesson
  4. resetOps = [{ partitionKey: partitionKey(PARTITION_DRIFT),           mutator: () => ({}) },
                 { partitionKey: partitionKey(PARTITION_FLOATING_GROUPS), mutator: () => [] }]
  5. await writeTransaction(resetOps)     // atomic — self-healing reset
  6. chrome.storage.session.remove('tj:tabClaims')                                      // best-effort
  7. return { itemsImported: items.length, groupsImported: groups.length, duplicatesSkipped, repairs? }
```

Step 5 failure logs a console.warn and does NOT reject the import — the items/groups write is the contract; the transient-state reset is cleanup. Step 6 failure is silent (session storage is ephemeral).

### §33.8 ULID Minting (C-4)

**Every imported item and group gets a fresh ULID.** No file-provided ID is ever reused.

**Algorithm:**

```
1. During parse: each record receives id = ulid() from background/storage/ids.js.
2. During parse: maintain an in-memory Map<oldId, newId> keyed by the FILE-PROVIDED id string.
   HTML: no file-provided IDs exist — the map is unused.
   JSON: populate the map as each record is parsed; every record in {items, groups} gets mapped.
3. During parse (JSON only): rewrite cross-references using the map:
   - For each item: item.groupId = oldToNew.get(item.groupId) ?? null
   - For each group: group.parentId = oldToNew.get(group.parentId) ?? null
   - A missed lookup (id was never defined in the file) → null — the repair pass's orphan handling (AC5/AC8) already covers this case.
4. Log map size + collision counter (COUNTS ONLY — never ids, never titles, never urls — per privacy rule in §33.9):
   console.log('[import]', { remaps: oldToNew.size, collisions: duplicateIds, source: 'json' })
```

**Why mint fresh:**

1. **Security:** a crafted JSON file could include an ID matching one that exists in another user's profile or a future Tab Junkie release. Minting fresh guarantees every imported record is freshly-identified, scoped to the importing profile's ULID time-prefix.
2. **Identity invariant:** §3 says "IDs are never reused after delete (fresh ULID every create)." Import is a create. Re-using file IDs would violate this invariant.
3. **Collision robustness:** the B-043 export includes a ULID; if a user exports, fiddles with the file, and re-imports, the crafted ULID might collide with an existing in-storage ULID (if they're re-importing on the same profile partially). Minting fresh removes the collision class entirely.

**Cost:** B-045 loses byte-equivalence of ULIDs across round-trip. This is an acceptable divergence from B-043 AC7's round-trip promise: the `schemaVersion` / `exportedAt` / `items[*].title/url/groupId` etc. round-trip intact; only the `id` changes. Users never see ULIDs (they see titles, groups), so this is invisible.

**Collision-check log:** after parse, `new Set(items.map(i => i.id)).size === items.length` must hold. If not (a parser bug), throw ERR_UNREPAIRABLE. Cheap defensive assertion — O(n).

### §33.9 Duplicate Handling (AC11 + AC12)

**Default behaviour per B-060 AC: skip duplicates by URL.** Both B-044 and B-045 always pass `skipDuplicates: true` at v1. B-060 later wires the UI toggle.

**Algorithm (in parse step, before commit):**

```
dedupeByUrl(items, options):
  seen = new Set()
  deduped = []
  duplicateUrls = 0
  for item of items (in §32.5.5 order):
    normalized = normalizeUrl(item.url, { forStorage: true })
    if seen.has(normalized):
      if !options.skipDuplicates:
        deduped.push(item)   // B-060 future path
      else:
        duplicateUrls++
      continue
    seen.add(normalized)
    deduped.push(item)
  return { items: deduped, duplicateUrls }
```

**Scope for B-044/B-045:** duplicates *within the file*. Because import is REPLACE, cross-file duplicate detection (against existing `tj:items`) is N/A — the existing store is discarded by commit. B-060's future UX (merge-import) extends this to cross-store duplicates.

**Count-preview dialog surfaces this:**

- `N` — total items that will be committed (post-dedup).
- `M` — total groups (post-repair).
- `D` — duplicate-URL skips (AC11 / AC12 count).
- `K` — malformed-entry skips (B-044 only).

### §33.10 Service-Worker Cold-Start Safety (C-3)

**Import is a user-initiated, interactive action.** The SW is alive when the handler runs (the sidepanel just dispatched `chrome.runtime.sendMessage`, which wakes the SW). Still:

- Handler `await readyPromise` BEFORE calling any storage partition read or the import entry point — matches the existing dispatcher pattern in `storage-handlers.js`. This is also what triggers migration-runner-aware safe-mode rejection with `ERR_SAFE_MODE`.
- `MSG_IMPORT_COLLECTION` is added to `WRITE_MESSAGE_TYPES` in `storage-handlers.js` so the safe-mode gate rejects it cleanly with `ERR_SAFE_MODE` (B-044 AC12 and B-045 AC3 requirement).
- The parse + commit happen in one JS turn — no awaits that yield to event-loop-reentrancy between parse and commit. If the SW suspends mid-commit, `writeTransaction` is designed to be either fully-applied or fully-absent (see `background/storage/write-transaction.js` single-writer invariant).
- No `storage.session` stash between preview and commit (§33.4 decision) — each message is independent, so an SW restart between the two messages just re-parses from scratch. The commit message carries the full file content; the SW doesn't need in-memory state to survive.

**Pre-dispatch oversize guard (defensive):** sidepanel rejects files > 5 MiB with an inline toast "File too large (max 5 MiB)." before reading. Rationale: `chrome.storage.local.QUOTA_BYTES` is 5 MiB total. A 10 MiB file is guaranteed to fail quota; rejecting early saves the user a round-trip and the SW a wasted parse. `ERR_QUOTA_EXCEEDED` surfaces post-parse if pre-check passes but the committed shape still exceeds quota (e.g., after repair expansion).

**Privacy rule (§32.9 parallel):** no error message logs the file content, titles, or URLs. Generic reason strings only. R4 [security-reviewer] greps the import diff for `console.*` sites that touch `item.title`, `item.url`, `group.name`, `href`, etc.

### §33.12 Performance Targets

| Phase | Input | Target | Measurement |
|---|---|---|---|
| **HTML parse** | 1000 `<A>`, 20 KB file | < 500 ms P95 | `performance.now()` around `parseNetscape`, median of 5 runs in chrome-mock |
| **JSON parse + validate** | 1000 items, 100 groups, 150 KB file | < 300 ms P95 | `performance.now()` around `validateAndRepair` |
| **Commit + broadcast** | 1000 items + 100 groups | < 500 ms P95 | `performance.now()` around `commitImport` + one `MSG_STATE_CHANGED` receipt |
| **End-to-end (user-perceived)** | 1000 items HTML or JSON | < 3 s P95, click → success toast | Covers pick → read → preview → confirm → commit → toast |
| **Parse phase alone (B-044 AC14)** | 1000-item HTML | < 500 ms | Same as HTML parse above |
| **End-to-end B-044 (AC14)** | 1000-item HTML | < 2000 ms | Replace-all click → success toast |
| **End-to-end B-045 (AC13)** | 1000-item JSON | < 1000 ms | Replace-and-import click → success toast |

**Budget logic:** B-044 AC14 allows 2000 ms (one round-trip, one writeTransaction, parse dominated by tokenizer + walk). B-045 AC13 requires 1000 ms (parse dominated by native `JSON.parse` — much faster than the tokenizer). The end-to-end 3 s target in this table includes file-read and preview-dialog-render time, which is outside the AC budgets.

**As-shipped measurements (B-044, Sprint 18 R5 e2e test):** on the seeded 1000-bookmark fixture, preview + commit measured **~11 ms** total (combined, not individual). Comfortably inside the AC14 2000 ms budget by two orders of magnitude — the hand-rolled tokenizer is materially faster than the DOMParser estimate baked into the original target. Budget retained as-written for margin; the AC-shipping reality is well under.

**Anti-patterns explicitly forbidden (mirrors §32.8):**

1. **No per-item storage reads** during parse/repair. All storage reads happen once upfront (the commit-side read of existing partitions is skipped — REPLACE doesn't need to know the prior state).
2. **No repeated `JSON.parse` calls.** One parse, in-memory walks thereafter.
3. **No `innerHTML` anywhere.** DOMParser output consumed via `.textContent` + `.getAttribute()` only.
4. **No nested async in the parse walk.** HTML/JSON parsers are sync; awaits only at commit boundary.
5. **No full re-sort inside loops.** One `Array.sort` per partition at the end of repair.

**Performance test harness (R5):** seeded 1000/100 fixture generator in `tests/fixtures/`, real `chrome.runtime.onMessage._listeners` dispatcher (Sprint 15 retro: no shim dispatcher), median of 5 runs asserted in the integration test.

### §33.13 Rollback Plan

**Imports are destructive (replace-all).** There is no auto-backup in B-044/B-045 scope.

**As-shipped behaviour (B-044, R6 confirmation):** import runs as a single atomic primary `writeTransaction` (§33.7). Safe-mode rejections, payload-validation failures, parse errors, and quota failures all fail BEFORE the transaction commits — pre-import state is preserved intact in every pre-commit failure path. Once the primary transaction resolves, items/groups are replaced; the subsequent reset transaction (drift/floating) and session claims wipe are self-healing cleanup and cannot partially corrupt the primary write.

**Documented caveat:** the Replace-all confirmation dialog (B-044 AC4, B-045 AC4) explicitly warns the user that existing data will be replaced. Users who want an "undo" must **first export** via B-042 (HTML) or B-043 (JSON) BEFORE importing — the existing export action is one menu entry away. There is no post-commit rollback surface inside the extension.

**No pre-import auto-snapshot shipped in Sprint 18.** A future improvement candidate (out of scope):

- **"Pre-import auto-backup"** — before commit, write current `tj:items + tj:groups + tj:prefs` to `storage.session.preImportSnapshot`, allow one-click restore for N minutes. Out of scope for B-044/B-045 because (a) it widens the atomicity surface (commit must now also clear the snapshot on success), (b) it adds a storage schema concern (snapshot format versioning), and (c) session storage doesn't survive browser restart, making the "restore" UX fragile.

**Schema-migration rollback:** if a B-045 import applied an in-memory migration (file at version < KNOWN_VERSION), the imported snapshot was migrated before commit. The migration is in-memory only; the storage schema is already at KNOWN_VERSION. Rollback of the extension version does NOT interact with the import — the commit wrote current-schema data.

**Rollback procedure (extension update causing import regression):** `git revert <sprint-18-merge-sha>` on `release/v2`. Existing panels continue to function. Users lose the Import action. Saved data is untouched because the `tj:items`/`tj:groups` shape has not changed — B-044/B-045 add no new persisted fields.
