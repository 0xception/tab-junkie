**Priority**
- **P0**: Critical — blocks launch or core value
- **P1**: High — essential for competitive product

- **S**: 2-8 hours (half day to one day)

- **done**: Completed and verified

| B-001a | As a developer, I want a partitioned `chrome.storage.local` schema with Item/Group/Preferences CRUD and ULID identifiers, so that all downstream features have a stable, writable data layer. | P0 | M | done | 1 | — ⚠️ **New storage schema** → Full tier; supersedes B-001 (split per R0 spike 2026-04-15) | **AC1** All six partitions are initialized under their exact keys (`tj:meta`, `tj:items`, `tj:groups`, `tj:prefs`, `tj:drift`, `tj:floatingGroups`) on first SW startup; a subsequent `chrome.storage.local.get` on each key returns a defined value (not `undefined`).<br>**AC2** `listItems()` and `listGroups()` return `[]` (empty array, not `undefined` or `null`) when storage contains no items or no groups respectively; a freshly initialized extension with no user data must satisfy this invariant without additional handling by callers.<br>**AC3** Every ID generated by a create operation is a valid ULID string (26 characters, Crockford Base32, monotonically sortable within the same millisecond); IDs are never re-used after delete; IDs are never derived from or contain any substring of the item's URL or title.<br>**AC4** `createGroup()` or `updateGroup()` with `parentId` set to a group that already has a non-null `parentId` is rejected synchronously with a typed error (`ERR_DEPTH_EXCEEDED`); setting `parentId` equal to the group's own ID or to any of its descendants is rejected with `ERR_CIRCULAR_REF`; no partial write reaches storage on rejection.<br>**AC5** Any call to a CRUD write function (create, update, delete) made directly from a UI context (sidepanel, newtab, popup) is rejected with `ERR_DIRECT_WRITE`; the only code path that calls `chrome.storage.local.set` is the service worker message handler; this is enforced structurally (write functions not exported to non-SW modules).<br>**AC6** `writeTransaction(ops)` executes all logical steps and commits to storage via a single `chrome.storage.local.set`; if the SW is terminated after the call resolves, a subsequent read reflects either the full committed state or the pre-transaction state — never a partial intermediate state; `writeTransaction` is the only mechanism used internally for any multi-key write.<br>**AC7** Deleting a group that contains items moves all those items to `groupId: null` (Ungrouped) in the same `writeTransaction` — no item is deleted as a side effect of group deletion; the resulting storage state contains zero items referencing the deleted group ID.<br>**AC8** Reading from storage when the stored value is structurally invalid (missing required fields, wrong type) returns a typed error (`ERR_CORRUPT_DATA`) rather than silently returning a malformed object or throwing an unhandled exception; the corrupt partition is isolated and does not prevent reads from other partitions.<br>**AC9** Single-item read (`getItem(id)`) and single-item write (`updateItem(id, patch)`) complete in under 20 ms P95 measured against a collection of 1,000 items in a test environment using the chrome-mock; this is asserted in the automated test suite.<br>**AC10** `writeTransaction` is re-entrant-safe: if two `writeTransaction` calls are initiated concurrently (e.g., two rapid UI messages arrive before the first resolves), they are serialized — the second call waits for the first to commit before executing; the final storage state reflects both operations applied sequentially with no lost update. |
| B-001b | As a developer, I want a schema version field plus a migration runner gated by a service-worker `ready` barrier, so that schema evolution is safe and downgrades fail closed into read-only safe-mode. | P0 | M | done | 2 | B-001a ⚠️ **Migration logic** → Full tier | **AC1 — Schema version gate (normal path):** On SW startup, `tj:meta.schemaVersion` is read before `readyPromise` resolves; if `schemaVersion === KNOWN_VERSION` (currently `1`), migrations are skipped and `readyPromise` resolves; any `chrome.runtime.onMessage` handler that `await`s `readyPromise` before processing confirms this gate is live by verifying message dispatch does not begin until the promise settles.<br>**AC2 — Fresh-install path:** When storage is completely empty (no `tj:meta` key), the migration runner initializePartitions seeds schemaVersion: 1; absence is handled by init, not by the migration runner; `initializePartitions()` runs; `tj:meta.schemaVersion` is written to `KNOWN_VERSION`; `readyPromise` resolves without error; no migration step is executed.<br>**AC3 — Corrupted or missing `schemaVersion` field:** When `tj:meta` exists but `schemaVersion` is absent, `null`, `NaN`, or a non-integer, the runner rejects `readyPromise` with `ERR_CORRUPT_DATA`; all write messages respond `ERR_NOT_READY`; read messages (`MSG_LIST_ITEMS`, `MSG_LIST_GROUPS`, `MSG_GET_PREFERENCES`) still resolve using the last-known partition data; the condition is observable in the automated test suite via a chrome-mock seeded with a corrupt meta partition.<br>**AC4 — Sequential multi-step migration (v1 → v2 → v3):** Given a migration registry with steps for v1→v2 and v2→v3, and storage seeded with `schemaVersion: 1`, the runner applies both steps in order within a single `writeTransaction`; the final `tj:meta.schemaVersion` equals `3`; if the v2→v3 step throws, `tj:meta` is left at `schemaVersion: 1` (no partial version bump); `readyPromise` rejects with `ERR_TX_CONFLICT`; the test asserts the version did not advance past the failed step.<br>**AC5 — Downgrade / read-only safe-mode:** When `stored.schemaVersion > KNOWN_VERSION`, `readyPromise` resolves (not rejects); all write messages (`MSG_CREATE_ITEM`, `MSG_UPDATE_ITEM`, `MSG_DELETE_ITEM`, `MSG_CREATE_GROUP`, `MSG_UPDATE_GROUP`, `MSG_DELETE_GROUP`, `MSG_SET_PREFERENCES`) return `{ ok: false, error: { code: 'ERR_SAFE_MODE' } }`; all read messages (`MSG_LIST_ITEMS`, `MSG_LIST_GROUPS`, `MSG_GET_ITEM`, `MSG_GET_GROUP`, `MSG_GET_PREFERENCES`) return `{ ok: true, data: … }` with current partition data; the safe-mode state is detectable via a new `MSG_GET_STATUS` message (or equivalent query) that returns `{ safeMode: true, schemaVersion: N, knownVersion: M }`; a test seeds `schemaVersion: 999` and asserts this behaviour pass/fail per message type.<br>**AC6 — Quota warning UX (80% threshold):** After every successful `writeTransaction`, the runner reads `lastQuotaSample.bytesInUse` via `_peekQuotaSample()`; if `bytesInUse / chrome.storage.local.QUOTA_BYTES >= 0.80`, a non-blocking quota-warning notification is surfaced to the UI (mechanism: a new message push or a flag readable via `MSG_GET_STATUS`); the warning does NOT block or delay the write that triggered it; it does NOT show on reads; it dismisses when the next sample falls below 80%; the automated test asserts the threshold trigger using a chrome-mock whose `getBytesInUse` returns a value at exactly 80% of `QUOTA_BYTES`.<br>**AC7 — Legacy `junkie_*` key migration:** On first SW startup where `junkie_*` keys are detected alongside `tj:*` keys, the runner copies any recoverable data into the `tj:*` schema (or discards if the shape is unrecognisable), then removes all `junkie_*` keys via `chrome.storage.local.remove()`; the removal executes within `readyPromise` before the gate opens; after the gate opens, a `chrome.storage.local.get()` on any `junkie_*` key returns `undefined`; if the removal itself fails, `readyPromise` still resolves (best-effort cleanup — orphaned legacy keys are not a blocking condition); the automated test seeds both key namespaces and asserts the `junkie_*` keys are absent post-startup.<br>**AC8 — CRUD-before-ready is rejected:** Any `chrome.runtime.onMessage` arriving while `readyPromise` is still pending (not yet resolved or rejected) is held until the promise settles, then processed normally if resolved or returned as `ERR_NOT_READY` if rejected; the message channel is never dropped; the test drives this by delaying `readyPromise` resolution and asserting the held message returns the correct outcome once the gate opens.<br>**AC9 — Migration runner performance:** A migration run over the maximum realistic dataset (1,000 items, 100 groups, preferences) completes within 500 ms in the chrome-mock test environment; this is asserted as a timed automated test.<br>**AC10 — Rollback plan documented:** `docs/SOLUTION_DESIGN.md` contains an updated §12 Rollback Plan entry describing: (a) how to revert B-001b code, (b) what happens to on-disk `tj:meta.schemaVersion` after a code rollback, and (c) how safe-mode protects users on downgrade; this entry is verifiable by the [solution-architect] at R6 close. |
| B-001c | As a developer, I want an in-memory `LiveTabIndex` plus a `storage.session` `TabClaims` disambiguation table, so that saved items correctly resolve to a specific live tab (including when multiple items share a URL). | P0 | M | done | 2 | B-001a ⚠️ **New message contract for live-state reads** → Full tier | **AC1 — Cold-start rebuild:** On SW cold start, `chrome.tabs.query({})` is called once; the result is used to populate `LiveTabIndex` (SW-memory `Map<tabId, {url, active, audible}>`) before any live-state read is served; the rebuild completes in under 100 ms for 50 open tabs in the chrome-mock test environment; this is asserted as a timed automated test.<br>**AC2 — TabClaims population on cold start:** After `LiveTabIndex` is built, `chrome.storage.session` is read for any surviving `TabClaims`; each claim is validated against `LiveTabIndex` (tabId still present, URL still matches); invalid claims are discarded; remaining unclaimed items with a URL present in `LiveTabIndex` are claimed in ascending `sortOrder` (first-unclaimed-wins); the final `TabClaims` state is written back to `storage.session` atomically; all of this completes before `readyPromise` resolves.<br>**AC3 — Multi-item URL disambiguation:** Given three saved items sharing the same URL and two open tabs at that URL, exactly two distinct items each receive a unique `tabId` claim and the third item's `live` state is `false`; no two `TabClaims` entries share the same `tabId`; this invariant is asserted in an automated test seeded with duplicate-URL items.<br>**AC4 — Tab-event in-memory updates (zero storage.local writes):** `chrome.tabs.onUpdated`, `chrome.tabs.onActivated`, and `chrome.tabs.onRemoved` each update `LiveTabIndex` in SW memory only; none of these handlers call `chrome.storage.local.set` or `writeTransaction`; the automated test spies on `chrome.storage.local.set` and asserts it is never invoked in response to any tab event.<br>**AC5 — Tab closed — claim cleanup:** When `chrome.tabs.onRemoved` fires for a tab that holds a `TabClaim`, the claim is removed from `storage.session` and the corresponding item's `live` state becomes `false`; the item is NOT deleted from `tj:items`; the update is reflected in the next `MSG_LIST_ITEMS` response.<br>**AC6 — Tab URL change — claim follows URL:** When `chrome.tabs.onUpdated` fires with a new URL for a claimed tab, the `LiveTabIndex` entry is updated; if the new URL no longer matches the claimed item's saved URL, the claim is released and reassigned (or dropped); if the new URL matches a different saved item, that item may receive a new claim in the next re-evaluation cycle; no `storage.local` write occurs.<br>**AC7 — Browser window closed — all claims for that window cleared:** When `chrome.windows.onRemoved` fires, all `TabClaims` entries whose `tabId` belonged to that window are removed from `storage.session`; the corresponding items' `live` states become `false`; this is asserted in an automated test that removes a window containing two claimed tabs.<br>**AC8 — storage.session wiped (browser restart) — re-claim on startup:** `storage.session` is cleared on browser restart by Chrome; on the next SW cold start, `TabClaims` is absent; the cold-start rebuild path in AC2 runs from scratch and re-establishes claims from live tabs; no stale claims from the previous session are carried forward.<br>**AC9 — Read-time live-state merge via enriched MSG_LIST_ITEMS:** The `MSG_LIST_ITEMS` response includes a new `liveStates` map alongside the `Item[]` array: `{ items: Item[], liveStates: Record<itemId, { live: boolean, active: boolean, audible: boolean }> }`; the map is built at read time from `LiveTabIndex` + `TabClaims`; items with no claim have `{ live: false, active: false, audible: false }`; no live-state field is stored on the `Item` object in `tj:items`; the shape change is documented in `shared/messages.js` and in `docs/SOLUTION_DESIGN.md`.<br>**AC10 — Claim resolution performance:** Building `TabClaims` from a 500-item collection against a 50-tab `LiveTabIndex` completes in under 50 ms in the chrome-mock test environment; this is asserted as a timed automated test. |
