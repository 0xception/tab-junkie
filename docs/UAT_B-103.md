# UAT — B-103 Promote-Tab Duplicate Bug Fix

**Sprint**: 35 · **Tier**: Full (S, tier-upgraded for regression coverage) · **Status**: pending UAT execution

**Context**: B-103 inherits the SHARED §50 fix with B-102 — `sidepanel/sidepanel.js` now calls `patchOpenTabsSection(_cachedOpenTabs)` immediately after `_setCachedOpenTabs(...)` in BOTH the `'noop'` and `'patch'` `diffAndPatch` fast-path branches (and AFTER the `_itemById` rebuild on the `'patch'` branch, per R4 H-1). Pre-fix symptom: after promoting an open tab into a saved bookmark, BOTH the new bookmark row AND the original Open Tabs row remain visible (the "duplicate" symptom from S33 B-099 UAT-13). Post-fix invariant: a tab appears as EITHER a live bookmark row OR an Open Tabs row — never both.

**Reference invariants** (post-fix):
- **Q1 invariant (locked R1)**: a tab can appear as either a live bookmark row OR an Open Tabs row — never both. Any UAT case showing the duplicate is a blocker FAIL.
- **Q2 invariant (locked R1, verified R2 §51.D-2)**: the SW handler awaits `createItem` → `claimTabForItem` BEFORE returning; the claim is established before the broadcast emits. If UAT-1 or UAT-2 shows even a brief duplicate flash (>50 ms), record as WARN with a screenshot — this could indicate a SW-side race that the §50 fix does not address.
- **§51.4 audible follow-up**: the audible icon may take up to ~1-2 seconds to appear on the new bookmark row because it depends on the next `LIVE_STATE` broadcast cycle. This is a documented timing gap, not a B-103 regression. WARN if delay exceeds 2 seconds.
